## ORM / Persistence Architecture

Primary ORM:

MikroORM

Primary Pattern:

Data Mapper with Unit of Work and Identity Map.

Purpose:

* Transactional Domain Persistence
* Entity Mapping
* Repository Pattern
* Unit of Work
* Identity Map
* Explicit Transaction Boundaries
* Migration Execution

Raw SQL required for:

* Reporting
* Analytics
* Dashboards
* Permission-Filtered Global Search
* Audit Search
* Bulk Imports
* Bulk Updates
* Recursive Organization Hierarchy Queries
* Materialized Views
* Event Replay Queries
* Performance-Critical Queries

Architecture Rule:

MikroORM is used for transactional business operations. Raw SQL is used for complex read models, analytics, reporting, dashboard widgets, permission-heavy queries, and bulk operations. Tnvios must not force all database access through ORM entity graphs.

Module Boundary Rule:

Modules must not depend on deep cross-module ORM relations. Cross-module integration must happen through application services, read models, query services, and events.

Production Rules:

* Automatic schema synchronization is prohibited in production.
* Lazy loading is prohibited.
* Active Record pattern is prohibited.
* Every write operation requiring multiple tables must run inside an explicit transaction boundary.
* Business mutations must write audit records and outbox events in the same transaction.
