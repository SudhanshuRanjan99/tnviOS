# Purpose

This document defines coding, architecture, testing, security, deployment, documentation, and operational standards for all Tnvios development.

Applies to:

* Core Platform
* Core Engines
* Modules
* AI Components
* APIs
* Frontend Applications
* Mobile Applications
* Infrastructure

# Engineering Principles

## Platform First

Always build reusable platform capabilities before module-specific solutions.

Good:

Workflow Engine

Notification Engine

Audit Engine

Permission Engine

Bad:

CRM-specific approval system

HR-specific notification system

---

## Modular First

Every business feature belongs to a module.

Core platform should remain minimal.

---

## Security First

Security is a requirement.

Not a future enhancement.

---

## Tenant First

Every business feature must support:

Tenant Isolation

Permission Isolation

## AI Ready

## ORM / Persistence Layer

Primary ORM:

MikroORM

Primary Pattern:

Data Mapper

Required ORM Capabilities:

Unit of Work

Identity Map

Explicit Entity Manager Transactions

Repository Pattern

Migrations

Raw SQL required for:

Reporting

Analytics

Dashboards

Permission-Filtered Search

Bulk Operations

Recursive Hierarchy Queries

Performance-Critical Queries

Rules:

MikroORM is used for transactional domain logic.

Raw SQL is used for reporting, analytics, complex reads, bulk operations, and performance-critical queries.

Modules must not use deep cross-module entity relations as integration boundaries. Cross-module integration must use services, events, read models, or query services.

Automatic schema synchronization is prohibited in production.

Lazy loading is prohibited.

Active Record pattern is prohibited.

---

## Cache, Queue, and Background Jobs

Cache:

Redis

Background Jobs:

BullMQ

Rules:

BullMQ is used for background jobs, scheduled work, retries, email delivery, file processing, imports, exports, report generation, webhook delivery, and asynchronous AI tasks.

BullMQ is not the domain event bus. Domain events use Redis Streams first and Kafka later.

# Platform Tooling Standards

## Monorepo Build System

Turborepo is required for builds, development, linting, type checking, tests, package orchestration, and cacheable monorepo tasks.

## Observability Stack

OpenTelemetry SDK is required for traces, metrics, and logs across API requests, workflows, jobs, event handlers, AI actions, email delivery, and imports/exports.

Every request, event, job, workflow, and AI action must carry a correlation ID.

## Testing Stack

Vitest is required for unit tests, integration tests, service tests, policy tests, workflow logic tests, schema tests, and form engine tests.

Playwright is required for end-to-end browser tests across onboarding, organization setup, module flows, permission denial, workflow approvals, file uploads, imports, exports, and portal experiences.

Database integration tests must use a real PostgreSQL test database through Docker or Testcontainers.

## Email Provider Standard

Resend is the default transactional email provider.

Tnvios must use an Email Provider abstraction. Modules may not call Resend directly. Future providers include Amazon SES, SMTP, SendGrid, Mailgun, and tenant-specific email gateways.

## AI, Search, and Content Stack

pgvector is required for embeddings, semantic retrieval, AI memory, and RAG over tenant-filtered data.

Vercel AI SDK is required for AI Gateway integration, streaming AI responses, tool calling, and AI user experience.

Typesense is the default user-facing search engine for fast search, autocomplete, faceting, filtering, and module search.

Tiptap is the standard rich text editor for documents, notes, comments, knowledge base, reports, templates, and AI-generated content.

## Planned Phase 2/3 Technologies

Temporal.io is reserved for durable long-running workflow execution behind the Tnvios Workflow Engine.

Novu is reserved as a possible notification infrastructure/provider behind the Tnvios Notification Engine.

Yjs is reserved for collaborative document state and CRDT-based editing.

PartyKit and ElectricSQL are reserved for realtime collaboration and local-first/offline sync if required.

ClickHouse is reserved for analytics, event analytics, audit analytics, telemetry, AI usage analytics, and large-scale reporting projections.

Trigger.dev and Inngest are excluded unless BullMQ and/or Temporal are removed from the architecture.
